# Create Patio — map intersection placement

## Problem Statement

A creator placing a new patio needs to see, in real space, where their 100×100m footprint lands on the world and whether it collides with patios that already exist. Without a top-down map and live collision feedback, they can't tell if their footprint overlaps a neighbor — which later degrades the rendered area — until it's too late.

## Solution

A new `/create-patio` page shows a top-down satellite map. A fixed orange 100×100m square sits at the center of the viewport and represents the patio being placed. As the user pans the map, the square stays pinned to center while existing (blue) patio squares slide underneath it. Wherever the center square overlaps a patio square, the overlap region is painted red and the border segments of both squares that fall inside that region turn red — an unmistakable, live collision signal.

## User Stories

1. As a creator, I want a dedicated `/create-patio` page, so that placing a new patio is a distinct flow from editing one.
2. As a creator, I want a top-down satellite map, so that I can recognize real-world locations while placing my patio.
3. As a creator, I want a 100×100m square fixed to the center of the viewport, so that I always know exactly where my new patio will be placed.
4. As a creator, I want the center square to stay pinned to the viewport center while I pan, so that I place the patio by moving the world, not the square.
5. As a creator, I want the center square sized in real meters, so that it grows when I zoom in and shrinks when I zoom out, always representing 100×100m on the ground.
6. As a creator, I want the center square rotated by an azimuth angle, so that the footprint matches the orientation I intend (default 34°).
7. As a creator, I want to see other patios as squares on the map, so that I understand what already exists around my chosen spot.
8. As a creator, I want existing patio squares anchored to their real geographic coordinates, so that they stay fixed to the ground as I pan and zoom.
9. As a creator, I want patio squares of varied sizes and orientations, so that the map reflects the real diversity of existing patios.
10. As a creator, I want the overlap between my square and any patio square painted red, so that I instantly see a collision.
11. As a creator, I want my square to be able to collide with several patios at once, each overlap painted red, so that no collision is missed in a crowded area.
12. As a creator, I want the border segments of both squares that fall inside an overlap turned red, so that the collision boundary is crisp and legible.
13. As a creator, I want the overlap to recompute live as I drag, so that feedback is immediate rather than appearing only after the map settles.
14. As a creator, I want both squares to show a soft inner gradient and a colored border (orange for mine, blue for existing), so that the placement matches the intended visual design.
15. As a creator, I want the map to open already zoomed to street level over a sensible starting location, so that squares are visible immediately without manual zooming.
16. As a maintainer, I want patios stored as a single GeoJSON feature collection, so that native map clustering (bubbles at low zoom) can be added later without restructuring the data.
17. As a maintainer, I want the azimuth held in component state with no UI yet, so that a future control panel can drive rotation by calling the existing setter.

## Implementation Decisions

### Scope
- Core mechanic only: map + center square + patio squares + intersection. The Figma chrome (header, right "New Patio" details panel, Map/Aerial toggle, zoom/compass/scale bar, bottom toolbar, "Create Patio" action) is explicitly out of scope for this PRD.

### Routing & module
- New route `create-patio.lazy.tsx` that renders a `CreatePatio` module. No loader, no `validateSearch` — no non-lazy half needed.
- `CreatePatio` module follows the standard folder anatomy and owns its map canvas, overlay, hooks, utils, constants, and types. Per the layering rule, the route renders only the module.

### Map
- Mapbox via `react-map-gl/mapbox` + new `mapbox-gl` dependency. Base style `mapbox://styles/mapbox/satellite-streets-v12`.
- New env var `VITE_MAPBOX_TOKEN`, added to `vite-env.d.ts` and mirrored in `envSchema`. The token is supplied by the developer.
- Map is top-down with no pitch, so every square projects to a rotated rectangle on screen (no perspective skew).
- Default camera: a hardcoded start coordinate (Barcelona, matching Figma) at street-level zoom (~16).

### Data
- Patios are generated by a deterministic, seeded mock: ~6–8 features at pseudo-random offsets around the start coordinate, each with its own size (80–160m) and azimuth. Deterministic output keeps the dev view stable across reloads.
- Patios are shaped as a GeoJSON `FeatureCollection` so native Mapbox clustering (`cluster: true` + circle/symbol layers) can be added later as a purely additive change. Bubble rendering and the zoom threshold swap are deferred.

### Center square
- Screen-fixed at the viewport center. Pixel size derived from 100m at the current latitude and zoom (meters→pixels), so it scales with zoom.
- Rotated by an azimuth value held in `useState` (default 34°). No control UI in this slice; the setter exists for a future panel.
- Its geographic footprint is derived by unprojecting the screen rectangle when needed.

### Rendering & intersection
- An absolute SVG overlay sits above the map and re-syncs on every map `move`/`render` event.
- Patio squares: project each feature's geographic corners to pixels each frame, draw as rotated rounded `<rect rx=24>`.
- Center square: a fixed rotated rounded `<rect>` at viewport center.
- Square styling per Figma: orange (`#ff6a00`) 4px border + radial inner gradient (light transparent center → solid `#ff7100` edge, ~0.55 opacity) + inset shadow `rgba(161,94,5,0.44)` for the center; blue equivalent (`#315be4`) for patios.
- Intersection is computed with SVG `clipPath`, not boolean geometry or turf. For each patio P that overlaps the center: a red-filled copy of the center rect clipped to P yields the red overlap region; the center's stroke clipped to P plus P's stroke clipped to the center yield the red border-inside segments. Rounded corners are respected exactly because the browser does the clipping.
- Only center-vs-patio overlaps are painted; patio-vs-patio overlaps are ignored.
- Exact red value to be lifted from the Figma intersection node during implementation.

### Deep modules (pure, isolatable)
- **Meters→pixels / geo projection helper** — converts a ground distance and a geographic point to screen pixels given the map's current camera. Simple input/output, no map mutation.
- **Square geometry** — given a center point, size, and azimuth, returns the four corners (and/or the rotated-rect transform). Pure.
- **Seeded patio generator** — given a seed and start coordinate, returns a stable `FeatureCollection`. Pure and deterministic.

## Testing Decisions

- The repository has no test runner configured, and project conventions say not to introduce one unless explicitly asked. No test runner is added by this PRD.
- A good test here would assert only external behavior of the pure helpers — e.g. "the seeded generator returns the same features for the same seed", "square geometry returns four corners at the expected offsets for a given azimuth", "meters→pixels scales correctly with zoom" — never internal call sequences or SVG node structure.
- The three deep modules (geo projection, square geometry, seeded generator) are the natural unit-test targets **if and when** a runner is introduced; they are designed to be testable in isolation precisely so that step is cheap later.
- Visual/interaction behavior (pinning to center, live red overlap while dragging) is verified manually in the running app, since there is no DOM/visual test harness in the repo.

## Out of Scope

- The right "New Patio" details panel, the overlap-detected warning text, and the "Create Patio" action.
- Page header, search, Map/Aerial toggle, zoom controls, compass, and scale bar.
- Bottom toolbar.
- Low-zoom cluster bubbles and the bubble↔square zoom threshold (architecture is cluster-ready; UI deferred).
- Azimuth control UI (slider/handle).
- Persisting a created patio or any backend write.
- Patio-vs-patio collision rendering.

## Further Notes

- The developer must supply a valid `VITE_MAPBOX_TOKEN` for the map to render and for manual verification.
- Reusing the existing maplibre + MapTiler satellite setup was considered (no new dep/token) but Mapbox was chosen per the developer's stated direction; clustering works identically in either engine, so a later swap is a single-file style change.
- The `clipPath` approach is the load-bearing simplification: it turns "pixel-perfect rounded-rect intersection" from a heavy boolean-geometry problem into a few clipped SVG nodes the browser renders exactly.
